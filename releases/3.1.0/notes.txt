xewe-os-tools 3.1.0

xewe-os-tools is the Python package behind every XeWe OS firmware project (`xewe`: setup, build,
flash, serial, provision, test, release, release-card, format, brand-lint) and the reusable GitHub
workflows the other repos call. 3.1.0 follows 3.0.1 and adds the release card, per-chip release
assets, a per-project partition scheme, `--define` for test and flash, and reliable flashing
through a native USB port that a host or container presents under another name.

CHANGED SINCE 3.0.1

- `xewe release-card` (init, record, render, verify, fingerprint): a generated release card that
  records what was tested on which tree, with redacted logs, and is checked again in CI. The card
  jobs are in ci.yml and in the core and modules workflows.
- Per-row release assets and a per-chip release workflow (xewe-release.yml), so a product release
  attaches one image, meta file and manifest per chip and board row.
- scripts/release.sh runs the checks and renders the card; `--prepare` and the tag run use the
  same clone and the same logs.
- `--define K=V` for `xewe test` and `xewe flash` (also `XEWE_TEST_DEFINES`), so a flashed image
  and the tested image are built with the same defines.
- `[build] partition_scheme` in xewe.toml selects the partition scheme per project (default
  `no_ota`). An image larger than the scheme's app partition fails the build.
- `xewe webui` exports a Flask UI to progmem headers and a sketch, and ships the porting prompt.
  The core CI runs arduino-lint in strict mode.
- Flashing a chip on the native USB-Serial/JTAG port (VID:PID 303a:1001) passes esptool
  `--before usb-reset`; other boards keep `default-reset`.
- A port's USB ids are read from sysfs by device number (Linux), and `/dev/xewe-usb` is scanned
  as well. `xewe boards`, `xewe flash` and `xewe doctor` now find a board whose node a host
  mirrors into a container under another name, and the "same board came back under a new name"
  check works for such nodes.

BREAKING

- None known.

INSTALL

- Projects: `[tools] ref = "3.1.0"` in xewe.toml, then `./setup.sh`.
- Workflow callers: `uses: xewe-labs/xewe-os-tools/.github/workflows/<workflow>.yml@3.1.0`.
- A project whose `build/tools` holds an older copy must re-run `./setup.sh` without
  `XEWE_TOOLS_SOURCE` to pick up this tag.

KNOWN LIMITATIONS

- `xewe provision` answers a `(y/n)` prompt it does not know with `n`. A firmware whose first boot
  asks its own questions (for example the LED wizard of xewe-led-os) must be answered by hand
  once; provision can then finish the Wi-Fi and module prompts (`--no-reset` after the wizard).
- Default core and modules refs in `src/xewe/env/pins.py` stay at 3.0.0, because core and modules
  are tagged after tools. xewe-os and the product pin their refs explicitly.

NOT VERIFIED

- The `usb-reset` flash and the mirrored-port lookup were run on one ESP32-C3 behind a Proxmox
  USB passthrough. They were not run on a C6 or an S3.
- Python 3.11 and 3.12 were not run on the machine that prepared this card; the CI matrix covers
  them.
- The card jobs of the calling workflows (core, modules, xewe-os, product) run for the first time
  against this tag.

TESTING

What was tested on which tree and with which result: release_card.md, generated by
scripts/release.sh --prepare 3.1.0 and attached to this release.
