## 6. Design decisions

- **Decision:** The key is `[build] partition_scheme`, a new optional table, default `no_ota`.
  **Why:** It is a build input, not a project identity field or a pinned source; a table leaves room for other board options without touching `[project]`. Requested placement by the human.
  **Alternatives rejected:** `[project] partition_scheme`; a free-form `board_options` string (would let a project change FlashSize or CDCOnBoot, which the tools treat as fixed).
- **Decision:** The manifest checks only the shape; the list of schemes and the size come from the installed core at build time (`boards.txt` + CSV).
  **Why:** The core is the truth and `[toolchain] esp32` can change it; a static copy in the tools would drift. Without an installed core the default scheme behaves exactly as before (arduino-cli checks the size).
  **Alternatives rejected:** a static scheme table in chips.py checked at parse time.
- **Decision:** Only schemes that fit the fixed 4 MB flash are accepted; `custom` is refused.
  **Why:** FlashSize=4M is fixed and the merged image is 4 MB; `custom` needs the sketch's own partitions.csv, which the staged sketch mirror does not copy.
  **Alternatives rejected:** none.
- **Decision:** The tools re-check the image size against the CSV's app partition and record it in meta.json (`app_partition_size`); the build summary line is unchanged.
  **Why:** arduino-cli already refuses an oversized image via `upload.maximum_size` (equal to the CSV app size for every 4 MB scheme in 3.3.12, checked); the tools' own check and record make the limit visible without changing an output line.
  **Alternatives rejected:** printing "of LIMIT" in the summary line (an output change for every project).
- **Decision:** No change to build_config.toml or firmware_map.csv.
  **Why:** neither records the FQBN or a build option today; meta.json does (fqbn, now also partition_scheme).
  **Alternatives rejected:** none.
